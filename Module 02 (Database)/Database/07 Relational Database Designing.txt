Keys
====
🧩 What are Keys?

> Keys are columns (or combinations of columns) that help identify records uniquely and establish relationships between tables.

They are used to:

=> Uniquely identify a record
=> Establishing relationships (through references)
=> Improving query performance

Types of Keys
-------------
Some of the many types of keys in RDBMS are:
1. Primary Key
2. Foreign Key
3. Composite Key
4. Alternate Key
5. Candidate Key
6. Super Key
7. Surrogate Key
8. Index Key (not for uniqueness, but for efficiency)

---

 🔹 1. Primary Key

> A column (or set of columns) that uniquely identifies each record in a table.
> It cannot contain NULL and must be unique.

🧱 Example Setup

We’ll use a Student–Course–Enrollment system to demonstrate all types of keys.

```sql
CREATE TABLE students (
    student_id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE,
    mobile VARCHAR(15) UNIQUE
);

CREATE TABLE courses (
    course_id INT AUTO_INCREMENT PRIMARY KEY,
    course_name VARCHAR(50) UNIQUE
);
```

Table 1: `students`

| student_id | name   | email            | mobile     |
| ---------- | ------ | ---------------- | ---------- |
| 1          | Vijaya | vijaya@gmail.com | 9876543210 |
| 2          | Sumati | sumati@gmail.com | 9999999999 |
| 3          | Jayesh | jayesh@gmail.com | 8888888888 |

Table 2: `courses`

| course_id | course_name |
| --------- | ----------- |
| 101       | Java        |
| 102       | Python      |
| 103       | PHP         |

👉 `student_id` uniquely identifies every student.
👉 `course_id` uniquely identifies every course.

* Both student_id and course_id are primary keys in their respective tables

---

 🔹 2. Foreign Key

> A column that establishes a relationship between two tables by referencing the Primary Key of another table.

Example:

```sql
CREATE TABLE enrollments (
    student_id INT,
    course_id INT,
    semester INT NOT NULL,
    PRIMARY KEY (student_id, course_id),         -- Composite Key
    FOREIGN KEY (student_id) REFERENCES students(student_id),  -- Foreign Key
    FOREIGN KEY (course_id) REFERENCES courses(course_id)       -- Foreign Key
);
```

👉 `student_id` and `course_id` are foreign keys referencing the parent tables.

---

 🔹 3. Composite Key

> A key made by combining two or more columns to uniquely identify a record.
> In the above table 
👉 The combination of `student_id` + `course_id` uniquely identifies each enrollment.
👉 A student can take multiple courses, but not the same course twice in one semester.

Table 3: `enrollments`

| enrollment_id | student_id | course_id | semester |
| ------------- | ---------- | --------- | -------- |
| 1             | 1          | 101       | 1        |
| 2             | 2          | 101       | 1        |
| 3             | 1          | 102       | 2        |

* student_id 1 can repeat, as the student has taken multiple courses
* course_id 101 can repeat, as more than one student can take the same course

* The combination - Student 1 Course 101 will never repeat

---

 🔹 4. Alternate Key

> When a table has multiple unique columns, one becomes the primary key and others are alternate keys (alternative ways to identify a record).

Example: In the students table

👉 `email` and `mobile` are alternate keys — unique identifiers other than the primary key.

---

 🔹 5. Candidate Key

> All columns that can uniquely identify a record are called candidate keys.
> From these, one is chosen as the Primary Key.

Example:

In the `students` table:
→ `student_id`, `email`, and `mobile` are all candidate keys.
→ We choose `student_id` as the primary key, and others become alternate keys.

---

 🔹 6. Super Key

> Any column or combination of columns that uniquely identifies a record.
> It may include extra unnecessary columns.
> A Super Key can contain non-unique attributes, provided it contains at least one Candidate Key.

Example:

=> `{student_id}` → Super Key ✅
=> `{student_id, name}` → Also a Super Key (but not minimal)
=> `{email}` → Super Key ✅

👉 Every candidate key is a super key, but not every super key is a candidate key.

All super keys:

|    | Super Key                           |
| -- | ----------------------------------- |
| 1  | { student_id }                      |
| 2  | { email }                           |
| 3  | { mobile }                          |
| 4  | { student_id, name }                |
| 5  | { student_id, email }               |
| 6  | { student_id, mobile }              |
| 7  | { email, name }                     |
| 8  | { email, mobile }                   |
| 9  | { mobile, name }                    |
| 10 | { student_id, email, name }         |
| 11 | { student_id, mobile, name }        |
| 12 | { email, mobile, name }             |
| 13 | { student_id, email, mobile }       |
| 14 | { student_id, email, mobile, name } |

* So, we have 14 super keys, while 3 of them are candidate keys, 1 is a primary key, 2 are alternate keys

---

 🔹 7. Surrogate Key

> A system-generated unique identifier (not derived from existing data).
> Usually an auto-increment value.

Example:

In our table:

```
CREATE TABLE students (
    student_id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE,
    mobile VARCHAR(15) UNIQUE
);
```

👉 `student_id` is a surrogate key, generated automatically by the database.

---

 🔹 8. Index Key

> An index is created on a column to speed up searching and sorting operations.
> It does not ensure uniqueness but improves performance.

Example:

```sql
CREATE INDEX idx_name ON students(name);
```

👉 The `idx_name` index helps MySQL find students faster when you query by name:

```sql
SELECT => FROM students WHERE name = 'Vijaya';
```

---

🧠 Summary Table

| Key Type      | Purpose                              | Example                         |
| ------------- | ------------------------------------ | ------------------------------- |
| Primary Key   | Uniquely identifies records          | `student_id`                    |
| Foreign Key   | Links two tables                     | `student_id` in `enrollments`   |
| Composite Key | Combination of multiple columns      | `(student_id, course_id)`       |
| Alternate Key | Unique column other than PK          | `email`, `mobile`               |
| Candidate Key | All possible unique identifiers      | `student_id`, `email`, `mobile` |
| Super Key     | Any unique column set (may be extra) | `{student_id, name}`            |
| Surrogate Key | Auto-generated key                   | `AUTO_INCREMENT id`             |
| Index Key     | Used for faster searching            | `INDEX(name)`                   |

Relationships
=============

In an RDBMS, data is stored in tables representing entities that are often inter-related.
These inter-table associations are called relationships.

There are three main types of relationships:

1. One-to-One (1:1)
2. One-to-Many (1:N)
3. Many-to-Many (M:N)

---

1. One-to-One Relationship

In a one-to-one relationship, each record in one table is related to exactly one record in another table.

Example: Employee and Address

| Employee | Address          |
| -------- | ---------------- |
| id       | emp_id *(PK, FK) |
| fname    | house_no         |
| mname    | street_address   |
| lname    | reference_point  |
| email    | city             |
| mobile   | state            |
| dob      | pin              |
| username | country          |
| password |                  |
| status   |                  |

🧩 Where to keep the Foreign Key:
The foreign key (emp_id) is usually placed in the secondary or dependent table (address), referencing the primary table (employee).

🧩 Important condition
To enforce 1:1: The foreign key must also be PRIMARY KEY or UNIQUE.

Relationship:
1 Employee ⟷ 1 Address

---

2. One-to-Many Relationship

In a one-to-many relationship, a single record in one table can be related to multiple records in another table.

Example: Department and Employee

| Department     | Employee       |
| -------------- | -------------- |
| dept_id *(PK)* | e_id *(PK)*    |
| dept_name      | e_name         |
|                | dept_id *(FK)* |

🧩 Where to keep the Foreign Key:
The foreign key (dept_id) is placed in the child table (Employee) that represents the “many” side.

Sample Data:

Department

| dept_id | dept_name |
| ------- | --------- |
| 1       | QA        |
| 2       | Dev       |
| 3       | BDA       |
| 4       | DevOps    |
| 5       | Admin     |

Employee

| e_id | e_name | dept_id |
| ---- | ------ | ------- |
| 1    | Ajay   | 2       |
| 2    | Harish | 1       |
| 3    | Harsh  | 1       |
| 4    | Jay    | 2       |
| 5    | Om     | 3       |

Relationship: 
1 Department ⟶ Many Employees
QA department ⟶ Harsh and Harish

---

3. Many-to-Many Relationship

In a many-to-many relationship, multiple records in one table can relate to multiple records in another.
To implement this, we use a junction (linking) table that contains foreign keys from both tables.

Example: Project and Employee

| Project     | Employee    | Project_Employee (Linking Table) |
| ----------- | ----------- | -------------------------------- |
| p_id *(PK)* | e_id *(PK)* | pa_id *(PK)*                     |
| p_name      | e_name      | p_id *(FK)*                      |
|             |             | e_id *(FK)*                      |

🧩 Where to keep the Foreign Keys:
Both foreign keys (p_id, e_id) are kept in the junction table (project_employee).

Sample Data:

Projects

| p_id | p_name |
| ---- | ------ |
| 1    | Bank   |
| 2    | Ecom   |
| 3    | CRM    |
| 4    | OMS    |

Employees

| e_id | e_name   |
| ---- | -------- |
| 1    | Ajay     |
| 2    | Harish   |
| 3    | Harshita |

Project_Employee

| pa_id | p_id | e_id |
| ----- | ---- | ---- |
| 1     | 1    | 1    |
| 2     | 1    | 3    |
| 3     | 2    | 2    |
| 4     | 2    | 3    |

Relationship:
Many Projects ↔ Many Employees
Project Bank (p_id:1) ↔ Ajay (1), Harshita (3) 
Project ECom (p_id:2) ↔ Harish (2), Harshita (3)

Normalization (Conceptual)
==========================

Before we learn normal forms, we must first understand why normalization is needed.

👉 Normalization exists to solve problems called *anomalies*.

---

What Are Anomalies?

> Anomalies are problems that occur in a poorly designed (unnormalized) database.

They happen when:

* Too much data is stored in one table
* Data is duplicated
* Table design mixes multiple entities

---

Types of Anomalies

1. Insertion Anomaly

* We cannot insert data without inserting unrelated data.

Example:

> Cannot add a new course unless at least one student is enrolled.

---

2. Update Anomaly

* Same data exists in multiple rows
* Updating one row but not others causes inconsistency

Example:

> Course name must be updated in many rows.

---

3. Deletion Anomaly

* Deleting a row removes unintended data

Example:

> Deleting the last student of a course deletes the course itself.

---

## What is Normalization?

> Normalization is a database design technique used to organize data in a way that reduces redundancy and eliminates anomalies.

Conceptually, normalization is about:

* Breaking large, messy tables into smaller, meaningful tables
* Ensuring each table represents one clear entity
* Storing each fact only once

---

## Why Normalization is Needed

Normalization helps us:

* Avoid duplicate data
* Prevent insertion, update, and deletion anomalies
* Maintain data consistency
* Improve data integrity

👉 Normalization is not about SQL syntax, it is about design thinking.

---

## Types of Normalization (Normal Forms)

Normalization is achieved by following a series of rules called Normal Forms.

---

1. First Normal Form (1NF)

Rule:

* Each column should contain atomic (indivisible) values
* No repeating groups or multi-valued attributes

Conceptually:

> One cell → one value

---

2. Second Normal Form (2NF)

Rule:

* Table must already be in 1NF
* Every non-key column must depend on the entire primary key

Conceptually:

> No partial dependency on a composite key

---

3. Third Normal Form (3NF)

Rule:

* Table must already be in 2NF
* No non-key column should depend on another non-key column

Conceptually:

> No transitive dependency

---

4. Boyce–Codd Normal Form (BCNF)

Rule:

* For every functional dependency, the determinant must be a candidate key

Why BCNF exists:

* 3NF can still allow subtle anomalies
* BCNF is a stricter version of 3NF

Conceptual idea:

> Only keys should determine other attributes

---

5. Fourth Normal Form (4NF)

Rule:

* Table must be in BCNF
* No multi-valued dependencies

Why 4NF exists:

* Sometimes attributes are independent but stored together
* Causes unnecessary duplication

Conceptual idea:

> One table should not represent multiple independent facts

---

## Conceptual Progression Summary

| Normal Form | Eliminates              |
| ----------- | ----------------------- |
| 1NF         | Repeating groups        |
| 2NF         | Partial dependency      |
| 3NF         | Transitive dependency   |
| BCNF        | Non-key determinants    |
| 4NF         | Multi-valued dependency |

---

## Important Practical Insight

* Most real-world systems stop at 3NF or BCNF
* 4NF is rare, but conceptually important
* Over-normalization can hurt performance

---

## Trainer-Grade One-Liner

> Normalization is the art of designing tables so that each fact is stored once, and anomalies are eliminated.
